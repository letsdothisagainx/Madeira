## Confirmed CPU fault producer

The exact packaged ARM64EC ntdll from Actions run `42533433436`, artifact
`13639280067`, has SHA-256
`975db861e62e49c254fedf87ba93dd8822f4f3e6d8f61cbec95f95e973062655`.
The inspection in Actions run `42538443337` confirms that native RVAs
`0x69d5c`, `0x6a4f4`, `0x6a514` and `0x6a520` implement
`wine/dlls/ntdll/sync.c:ios_srw_note()`. They increment the diagnostic history
index at RVA `0xe0a58`, select one of 512 entries at RVA `0xe0a60`, and store
the original lock pointer and thread/mode value. These are diagnostic writes,
separate from the actual Windows SRW-lock implementation.

The existing executable image copy made these native data addresses RX.
Each index update and two history writes could therefore require Mach recovery.
The correction extends the existing private, source-built ntdll writer contract
to the diagnostic ring and index. Only an unpublished image binds its writers
to that image's matching RW alias. Unknown contracts retain the original path;
no instruction is skipped, lock disabled or successful atomic result invented.
The real lock bodies and every history event remain intact. The two writer
fields and existing counter writer survive full and partial source-data refresh
without being transiently replaced by NULL or parent-image pointers.

Concurrent source refresh can still replace history payloads, as before this
change. The binding tests establish pointer stability during such refresh;
they do not establish event retention across it. Existing mapping selection
and lifetime rules remain in force; the PE contract alone is not a proof of
the complete VM registry's generation isolation.

The capture totals are 84,633,294 emulated stores and 399,803 ms cumulative
handler processing. These are not game-thread wall time, and removing this
producer does not eliminate all remaining faults. FEX statistics writes and
other legitimate stores remain separate investigation targets. The matched
before/after benchmark forces and checks the captured 32-bit LDAXR/STLXR retry
family rather than substituting a host LSE-only microbenchmark. Device FPS or
startup improvements must be measured in a new comparable run.

The six confirmed SRW sites present in bounded rank reports account for at
least 8,498,724 faults. Rank reports omit other keys; this is a lower bound,
not attribution of all GPR/exclusive faults to the history ring. In particular,
a late epoch's instruction-family percentages are not SRW site percentages.

Apple-host run `42540977023` measured 3,200 actual staged history events across

## Confirmed DirectX image-domain defect

The official `infinst.exe` child prefers `0x100000000` and has
`RELOCS_STRIPPED` with an empty relocation directory. The capture's host
mapping floor is `0x1044f8000`. The old subfloor translation cutoff was exactly
4 GiB, so this image bypassed the existing translated-image path and Wine
correctly returned `STATUS_CONFLICTING_ADDRESSES` (`0xc0000018`). Rewriting only
an image header or pretending relocation succeeded would be insufficient.

The correction extends the existing logical-address/backing-address contract
for eligible initial fixed AMD64 images entirely below the actual host floor.
Logical addresses, including the high bit at 4 GiB, remain distinct from their
owned backing. Native VM/fault lookup, FEX instruction/data translation and
SMC protection/invalidation must agree. A private versioned DATA capability is
read before the FEX image becomes guest-protected; old or mismatched backends
must fail before guest execution rather than receiving an incompatible control
message. Null pages, active mappings and guards are not mapped over.

The iOS frontend computes this logical address using integer address arithmetic
before casting it back to its encoded pointer. Clang's sanitizer caught the old
pointer expression forming an intermediate null pointer when the stream and
entry point were both 4 GiB. The corrected staged frontend remains fully
sanitized and preserves the logical address and backing bytes.

The new main-image descriptor publishes immutable coordinates and retires
atomically without reviving an old alias. Native registry readers validate a
publication generation; a successful unmap retires the corresponding alias
after invalidating both code names. The historical failed-unmap tracker
invalidation remains unchanged and is not claimed to restore permissions.
The ARM64EC alias translation unit uses the existing Cortex-A78 tuning applied
to FEXCore. An actual COFF-object gate requires supported CASAL32/CASAL64 and
release publication, rejecting exclusive-store lowering before CPU packaging.
An option string or a synthetic object fixture is not that compiled-object
proof; the gate runs on the candidate object during its real build.

No application-owned "installed" registry result or completion stamp is
created. The genuine Microsoft setup and Steam installscript remain responsible
for their exit results and persistent completion state. Production-function
regressions are not a successful execution of the official installer. Its
actual final exit, installed components and absence of a repeat next launch
remain device acceptance tests.

New app/native events share validated `CLOCK_MONOTONIC` origin timestamps.
One origin anchor also correlates Metal's monotonic timestamps with elapsed
startup time without logging private metadata.
They distinguish process request, child creation, API return, PE entry, exit
request and lease-proven quiescence. Nested process intervals overlap and must
not be summed as CPU time. Unobserved intervals remain unattributed; creating
CS2 does not prove that its menu is interactive or a practice map is rendered.

At least 192 Present calls occur. Sampled GPU work is about 2 ms/frame and
Present itself averages 1–3 ms, while the largest inter-Present gap is 211.8 s.
The primary measured delay is between Presents. The capture does not prove a
BC sampling, typeless/sRGB view or missing-material defect. Existing native BC
mapping and usage-flag code looks consistent; successful texture requests alone
are not proof of valid rendered output.

Owned DXMT build-copy probes now report actual Metal creation/view failures,
formats, bounded upload samples, pipeline errors/compile durations and distinct
draw/submit/GPU-completion/display events. They preserve all original Metal
calls and results. A 64-byte prefix hash is a sample, not complete subresource
integrity; native Metal errors are not invented D3D11 HRESULTs. A display event
is not a menu-interactivity assertion.

## Memory and connection limits

The pool stays 1152 MiB, with 240 MiB soft image headroom and the existing
512 MiB fresh large-code growth budget. No memory limit is increased. The late
SHELL32 allocation failure belongs to `steamerrorreporter64.exe`; it must not
be reported as another failure to load client.dll or embree3.dll.

Late footprint reaches roughly 5,850–5,870 MiB (about 5.7 GiB) against the 6 GiB budget, with about
2.2 GiB compressed. The largest sampled Metal allocation is 1478 MiB; logical
resource capacity and requested texture bytes are not physical GPU residency
and must not be added blindly to process footprint. Thermal state moves from
nominal to fair to serious. No actual CPU frequency trace establishes a
specific downclock; the emulated registry's 1000 MHz value is not such a trace.
Repeated 16 MiB FEX generation rotations are a remaining capacity/performance
concern, not permission to reclaim referenced code or grow the pool.

The capture contains no precise VAC rejection. Loading `steamclient64.dll`
does not prove a successful authenticated secure session. The two missing TOS
ancillary-data messages do not establish the VAC cause. CS2's normal
`-condebug` argument and a bounded successful-write observer expose fixed
connection/security event classes and explicit result numbers when genuine
Steam, game or service logs contain them. Raw text, credentials, IDs, endpoints
and private paths are not exported. Absence of a message is not authentication
success, and Valve-side unsupported matchmaking cannot yet be concluded.

## Device acceptance and rollback

Install the new IPA as a SideStore update to the existing Madeira app using the
same bundle/signing identity. Keep the installed app and its data; do not
uninstall, reset the prefix or redownload Steam/CS2. An older IPA can likewise
be installed as an update for rollback without manually editing phone files.

The next comparable device run must establish genuine DirectX completion and
next-launch reuse, CS2 process/menu/practice-map timing, actual frame output,
exception rates, memory/thermal behavior and the specific Steam/VAC result.
Host tests and a successfully built IPA do not establish those outcomes.
