and fewer tiny carves. That difference alone invalidates the earlier successful
embree replay as a prediction of this run.

At grant line 35397, an already quiescent helper's matching retired 16 MiB
receipt is only two seconds old. At line 37923 another such receipt is two

## Separate low-VA probes

The client backing-view probe at line 47237 fails in the low window with
`EEXIST`, 19 attempts and 19 occupied-region skips. Its first candidate
`0x2fd650000` lies inside a native read-only Mach mapping
`0x2b8000000+0x48000000`. Wine's view-tree gap counter does not include all Mach
mappings and JIT aliases. No-clobber placement correctly refuses that candidate.
Wine subsequently maps the real image backing at `0xfb7f50000`; the later pool
copy fails. Server shows the same successful higher-range fallback. Diagnostics
now label these as local-window probes with Wine-view-only gaps; they no longer
claim the outer image load has already failed.

## Code-buffer guards remain a separate limitation

The captured guard request covers the last 4 KiB of a direct pool code carve.
`NtProtectVirtualMemory` rejects it before a kernel call because this carve has
no ordinary Wine view. The host page is 16 KiB, and 12 KiB of that host page is
still within FEX's usable code bounds. Rounding down would protect valid code.
The established pool policy also avoids changing RX protection because later
executable restoration can fail on this platform. A new physical guard cannot
be declared safe from a host shim that supplies a successful protection call.

The production-path contract regression makes that limitation explicit. This
change does not suppress the error, fabricate protection success, change the
global guest page size or revoke executable access from a live buffer.
See `FEX_CODE_GUARD_CONTRACT.md` for the guarded-boundary evidence.
