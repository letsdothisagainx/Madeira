The former soft headroom policy depends on allocation order. It also exempted
minimum-sized code allocations from the large-growth cap. Repeated minimum
allocations could therefore consume the intended future image capacity.
Waiting longer for a retired buffer cannot guarantee the missing capacity.

The new fixture records all 45 granted code allocations and 77 lifecycle
events through the failure. One request exhausts its three-second retry period
while other threads allocate, release and retire buffers. Replaying it only at
completion incorrectly gives it a second retry period and predicts reuse that
did not happen. The negative replay preserves that continuation state and
matches every observed grant address and size. A separate pthread test proves
the overlapping-wait distinction. Unknown image-freelist coordinates remain
explicit synthetic inputs to the negative capacity control, not captured data.

## Production allocation changes

CS2 selects a **768 MiB low image arena and a 384 MiB high code arena** before
Wine allocation begins, within the same 1152 MiB backing. These are hard bounds,
not borrowed space or a prediction of future DLL timing. The native tail CAS
checks the partition for every request, including tiny and minimum-sized ones.
The image bump, freelist and tagged allocation paths enforce the image bound.
Code cannot borrow image freelists or region C, and ordinary code frees cannot
be promoted into image space in a partitioned session. Legacy sessions retain
their existing shared-arena policy and retirement recycler.

The image budget derives from the measured 632.9375 MiB pre-client footprint,
client.dll, embree3.dll and 12.296875 MiB of actual later image sizes from earlier
menu sessions: 708.03125 MiB altogether. Adding the prior 48 MiB safety margin
and rounding to a 64 MiB boundary yields 768 MiB. This is a measured bounded
startup budget, not a promise that every future game version fits.

The staged FEX producer starts at 16 MiB and grows from the **previous actual
grant**, through 32, 64 and 128 MiB. It no longer jumps from every small grant
straight to 128 MiB in this mode. Native refusal invokes the existing halving
ladder; a degraded 16 MiB grant makes the next growth request 32 MiB. Existing
generation references and thread migration retain old buffers until release.
Both ARM64EC and WoW64 use the owned overlay, leaving pinned vendor files intact.

## Real terminal guards

The old FEX constructor excluded 4 KiB, but Wine had no view for direct pool
carves and rejected its protection request. Rounding that request down would
remove execute access from 12 KiB that FEX still considered usable.

The versioned guarded-allocation contract instead excludes a full 16 KiB from
each code-buffer class. Native allocation protects that terminal page in both
aliases before publishing a pointer. A partial failure quarantines the carve
and returns failure. No guard is restored to executable or writable access.
Reuse is exact-class only and prefills only the usable body. Owner/lease-bound
confirmation verifies a successfully armed, live carve; a denial bitmap alone
cannot certify successful protection. Retired guarded reuse requires matching
nonzero retirement identity. Generic allocations cannot consume guarded carves.

Mach and BSD faults in either guard alias bypass store emulation, SMC repair,
alignment recovery and transient retry. Wine receives the original access
violation without PC advancement. Alias translation and complete store spans
also reject guard intersections. See [the guard contract](FEX_CODE_GUARD_CONTRACT.md).

## Image lifetime audit

The capture contains 579 image-copy records. The repeated same-base/name/size
rsaenh record reuses the same pool address through existing in-place rebuilding;
it is not a demonstrated duplicate allocation. Failed-import image retention
can preserve dependency references and is not proof of a leak. No new sharing
of process-private relocated image pages or reclamation of unproved receipts
is introduced. Existing quiescent process reclamation remains checked.

## Verification scope

The host regression compiles the actual native allocation/release paths and
literal staged CodeBuffer constructor and manager. OS adapters provide real
shared RX/RW mappings; they do not replace allocation or growth decisions.
Code-first, image-first and interleaved orders use four live managers and 17
miscellaneous code allocations. All load the conservative measured image
footprint, client.dll, embree3.dll and the 15 historical later image sizes.
The resulting image head is **708.03125 MiB**, leaving **59.96875 MiB** in the
image arena. Code reserves **352.265625 MiB**, within 384 MiB. The last live
classes are 16/32/64/64 MiB. Further actual manager rotations, full quiescent
retirement and successor reuse are exercised. A request beyond true capacity
still fails. Historical November 6–10 policies remain negative/legacy controls.

An explicitly **synthetic** extra 32 MiB image followed by a 16 MiB image also
fits in each order and remains mapped during 32 subsequent manager rotations.
That raises the image head to 756.03125 MiB and leaves 11.96875 MiB. A following
16 MiB image fails honestly. These are stress requests, not observed later DLLs.
The harness does not model all 127 native threads or arbitrarily many retained
generation references; a truly exhausted code arena must still report failure.

Separate tests execute guarded body code, fault reads/writes/execution at both
physical guard aliases, inject protection failures, and reject stale/foreign
confirmations. Signal tests compile actual recovery helpers and check access
violation records, whole-span refusal and unchanged registers/PC. Apple CI
also runs the existing native ARM64 atomic and alias regressions.

These are production-path host tests, **not an iPhone Steam/FEX compiler/game
run**. Actual compilation pressure, game initialization and the menu remain
device acceptance requirements. No before/after iPhone FPS or timing is claimed.

## Compressed run export and installation

**Export Run Diagnostics** in Madeira's diagnostics/settings and in-game menu
creates a ZIP whose text entries use actual raw DEFLATE compression. It includes
bounded sanitized startup/recent Madeira output, real CS2 console output,
allowlisted Steam logs, native/build policy, timing/error markers and the existing
focused VAC package. Its manifest records unavailable, sanitized and omitted
data. It never recursively exports the prefix, account databases or arbitrary
paths. File ownership and no-follow checks remain enforced; save backups retain
their existing default ZIP storage method. Collection is explicit and cancellable.

Install the new IPA over Madeira using the existing iPhone signing method and
same app identity. Do not uninstall or reset app data. No prefix/game migration
or manual configuration change is needed. Rollback is an in-place install of a
previous same-identity IPA; the code changes are separately revertible.

The pool backing and iOS memory cap are unchanged. RX/RW aliasing shares backing
but still consumes two VA ranges. This policy cannot guarantee gameplay asset
residency near the approximately 6144 MiB limit. Real-device acceptance requires
client.dll and embree3.dll loading, continued FEX compilation, usable menu and
memory safety. VAC secure matchmaking and graphics correctness remain unresolved;
neither CI nor Steam login establishes them.
