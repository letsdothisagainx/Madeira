## What the capture establishes

The previous LDRSW x18 fault (`b9980e48`) and invalid Chromium logging
argument do not recur. Steam and the real Crashpad subprocess now start.
The new failure is an execution-state/ownership cascade, not another missing
x18 load encoding.

`0x33eff8354` is a generated FEX dispatcher address, not a Mach-O offset to
subtract from Madeira.debug.dylib. Its preceding instruction `52800001`
sets w1 to zero; `f9400021` is `ldr x1,[x1]`. This matches the pinned FEX
`Dispatcher.cpp` **GuestSignal_SIGSEGV** trampoline. FEX deliberately generates
this native fault to report a guest fault. Repairing x1, restoring x18 here,
or skipping the instruction changes the meaning of a real guest exception.

The producer is visible immediately before the trap (lines 8961–8962):
`NoExec instruction in entry block: FFE7EF90`. Earlier (line 6907), Crashpad
published precisely `0xffe7ef90` as its i386 ntdll LdrInitializeThunk. The
faulting webhelper thread is 00ac, process 0064, TEB `0x6002d0000`, with FEX
ThreadState `0xdba001000` and CpuStateFrame `0xdba001140`. Its own ntdll was
mapped at guest `0xfff40000`, rather than Crashpad's `0xffe30000`.

The source explains how one process receives another's startup exports:

* `load_ntdll_wow64_functions()` overwrote the session-global
  `LdrSystemDllInitBlock` every time a child mapped ntdll32. Both the Unix
  initial-context producer and the private native ntdll data inherited those
  shared exports. Parent worker threads continue running during child boot.
* Crashpad's reservation (line 6875) incorrectly reports Steam's already-live
  window B=`0x400000000`. Its PEB is subsequently `0x406c60000`, inside that
  window. There is no new reservation/binding event. The old bootstrap lookup
  accepted a matching recycled `pthread_t`, or an inherited current process,
  as an already-established reservation; binding then silently refused the
  occupied slot. Crashpad worker PEBs consequently could not resolve a window.
  Their i386 debug-string pointers were subsequently read as native low
  addresses in `ios_log_throttle_drop`.
* An earlier native failure (line 6276) is symbolicated in the capture as
  `exit_thread+0x88`, reading a previous process's TEB at `0x6002f03a0`.
  `exit_thread` had one session-wide deferred TEB and thread count. Its next
  caller could dereference a TEB whose process window had already been reused.

`TEB+0x1788` is **ChpeV2CpuAreaInfo**, allocated for the AMD64/ARM64EC path.
A null value there is expected for an i386 thread. Its FEX state is in TLS14;
the i386 CPU-reserved context is a separate WoW64 TLS entry. A low 32-bit RSP
is likewise not proof of corruption: it is interpreted in that process's
window. New diagnostics follow TLS14's actual **CurrentFrame** pointer rather
than assuming the embedded frame is always at offset 0x140.

## Changes

* Reserve windows with an explicit per-thread reservation token and generation.
  A recycled pthread identity cannot borrow a bound window. Check binding before
  starting an i386 child; bootstrap failure reports failure and closes its own
  server connection.
* Register the root image identity as well as children, so child bootstrap
  cannot temporarily change its architecture classification. Keep ntdll32
  startup exports with their PEB. Seed each child's private native
  ntdll data through an exact-owner write; no fallback to another process's
  pool mapping. Initial i386 contexts use their own startup block and PEB32.
* Keep thread counts and deferred TEB/pthread snapshots per process. Serialize
  deferred joins per owner; never hold the global registry lock across a join.
  Forget bookkeeping before window teardown. A busy reaper retains its window.
* Close the failed process's server connection immediately, but retain its JIT,
  guest-window and image resources while other Wine threads remain. The last
  retiring thread releases them; late fixed-image teardown uses validated local
  view cleanup rather than an RPC on the dead connection. Unbound bootstrap
  cleanup cannot release a bound process's quarantined window.
* Remove the SIGSEGV loop's instruction skip and fabricated `0xDEAD0001` return,
  and remove the Mach terminal that killed the entire iOS task. An explicit FEX
  guest-fault trampoline receives normal exception delivery first. Dense repeated
  identical guest entry failures are bounded per thread/owner and end with
  `STATUS_ACCESS_VIOLATION` through real Wine termination. Only an exact live
  code-carve owner and a self-consistent TEB/TLS14 frame qualify. Original
  registers are logged with bounded `write()` output; termination runs on the
  original thread after signal/Mach return and native stack validation.
* Native faults with no verified guest stack are declined for native crash
  reporting; no best-effort guest frame is written onto an arbitrary stack.
  Threads of a dead owner retire through native Wine bookkeeping rather than
  raw Mach termination that bypasses it.

## Separate protection, Chromium and presentation findings

The guard diagnostics provide an actual result, not just the FEX message:
line 699 requests `0x33fffb000+0x1000`, receives `c000000d`
(`STATUS_INVALID_PARAMETER`), has **no Wine view**, and finds a live 16 MB
code carve owned by Steam. The kernel query succeeds, host page size is 16 KB,
and that page remains RX (prot=5, max=7). Later processes show the same shape.
This protection request really fails. Its relationship to the bad startup
exports is not established, and it must not be treated as successful.

Separately, the pinned FEX Windows allocator returns
`::VirtualProtect(...) == 0` as its success Boolean, while its WinAPI wrapper
returns true on NTSTATUS success. Thus the shared “Failed to mprotect” warning
can also report an actual successful request. Madeira now samples **both**
successful and failed NOACCESS results with their mapping/owner data; it does
not invert API results or suppress errors. No FEX source is changed:
[FEX/AGENTS.md](../../FEX/AGENTS.md) says “AI must not be used to generate code
for contributions to this project.” Correct support for a 4 KB tail guard in
the 16 KB JIT-carve mapping remains unresolved; no enlarged physical guard or
fabricated successful protection is introduced.

The latest Chromium `Check failed: false` precedes the first recorded NoExec
trap, so this capture does **not** prove that the check is caused by that trap.
The attached CEF file contains older sessions and almost no detail for this
attempt. Existing ShowWindow/SetWindowPos/host diagnostics show hidden windows
without a completed main-interface show/presentation or rendered contents.
There is no evidence justifying forced visibility. No window flags, Chromium
arguments, graphics DLLs, or Valve files are changed in this patch.

Low-address refusal reports include Crashpad debug-string accesses with no
registered window. A new private window addresses that demonstrated ownership
error; unrelated low-address allocation failures are not silently retried or
converted into invented mappings. SDL2/Vulkan inventory and loader diagnostics
from the previous build remain available; their UI impact still needs evidence.
